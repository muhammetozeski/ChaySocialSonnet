# Lessons

Short "problem -> fix" notes so the same wall isn't hit twice. See `docs/` for the longer write-ups
linked below.

- **Blazor `@rendermode` directive on a `@page` component uses space syntax, not an attribute-style quoted value.** `@rendermode SomeExpression` (no `=`, no quotes) — `@rendermode="SomeExpression"` throws `RZ1011`. Attribute-style quoted syntax is only for using a component as a child in markup (e.g. `<Routes @rendermode="X" />`).
- **`InteractiveAuto` + a per-page `InteractiveWebAssembly` override throws on first visit.** Auto tries an Interactive Server circuit first, which cannot host a WebAssembly-only component. Fix: don't mix them — if any page needs guaranteed client-side execution, make the whole app's render mode explicit (no Auto) via one host-configured switch. Full write-up: [docs/render-mode-auto-vs-per-page-override.md](docs/render-mode-auto-vs-per-page-override.md).
- **MAUI BlazorWebView throws if a shared Razor Class Library component declares any `@rendermode`.** BlazorWebView always runs interactively in-process and has no Server/WebAssembly split concept at all. Fix: gate the render mode behind a static, host-configured property (`HostRenderMode.Interactive`) that the Web host sets and MAUI leaves null.
- **A page that `@inherits` a base class already exposing `[Inject] NavigationManager NavManager` must not re-`@inject` its own `NavManager`.** Doing so compiles but emits `CS0108` (member hides inherited member) and is pure duplication — just use the inherited one.
- **A component that defines a `<style>` block still needs to actually be referenced in markup — a companion CSS component isn't auto-included by naming convention.** `MainLayoutCss.razor` (the aurora background, body font, `@font-face`) existed and compiled fine but `MainLayout.razor` never rendered `<MainLayoutCss />` anywhere, so none of it ever reached the DOM — every screenshot this whole session showed a flat black background and whatever font the browser defaulted to, not a bug in the CSS itself. Compiling clean proves nothing about a `*Css.razor` component actually being included; check the DOM (`document.querySelectorAll('style')`) when a style change doesn't visibly show up, don't assume the CSS itself is wrong.
- **A self-hosted `@font-face` needs the RCL-correct static-asset path.** A Razor Class Library's `wwwroot/` files are served at `_content/{ProjectName}/...`, not at the plain relative path a consuming app's own `wwwroot` would use — `url("fonts/x.woff2")` 404s silently (font-family just falls through to the next stack entry with no visible error); it must be `url("_content/MainProject/fonts/x.woff2")`.
- **`CoreCard`'s base CSS (`.core-card { flex-direction: column }`) always wins unless a `CustomClass` explicitly overrides it.** A `CustomClass` that only sets `display: flex; align-items: center;` (meaning to lay children out in a row) still stacks them vertically, because nothing in that rule touches `flex-direction` — `.core-card`'s `column` is the only declaration for that property and applies regardless of which style block loads later. Any `CustomClass` on `GlassCard`/`CoreCard` meant to be a row must say `flex-direction: row;` explicitly.
- **A `Microsoft.Maui.Graphics.Color` interpolated directly into a Razor `<style>` block (`color: @AppColors.TextMuted;`) renders as its raw debug `ToString()` (`[Color: Red=... Green=... Blue=... Alpha=...]`), which is invalid CSS.** The browser silently drops just that one declaration and the element falls back to its inherited color — no console error, no visibly "broken" look, just the wrong (usually too-bright) color and a lost visual-hierarchy cue. Always call `.ToRgbaHex(true)` explicitly (`color: @(AppColors.TextMuted.ToRgbaHex(true));`) — this bit ~30 call sites across the codebase (fixed 2026-09-04) before the pattern was caught by inspecting a live element's `innerHTML`, not by looking at a screenshot.
- **Minimal-API `MapDelete`/`MapGet` reject an inferred request body — an unmarked complex-type parameter next to a route parameter throws at app *startup*, not at request time, and `dotnet build` never catches it.** `MapDelete("/x/{id}", (string id, SomeRequest body, ...) => ...)` compiles clean but the app crashes on `dotnet run`/`preview_start` with `InvalidOperationException: Body was inferred but the method does not allow inferred body parameters` — DELETE/GET need an explicit `[FromBody]` on that parameter (POST/PUT infer it fine). This is exactly why "build succeeded" isn't enough for endpoint-mapping code; the app has to actually start. Full write-up: [docs/minimal-api-delete-get-body-inference.md](docs/minimal-api-delete-get-body-inference.md).
- **This app hides the bottom tab bar outside the 5 primary routes** (`NavigationRouting.IsBottomNavigationRoute`, checked in `MainLayout`) — any new route added outside `/home /search /messages /notifications /profile` renders with no nav at all unless it brings its own way back (e.g. a `<BackButton>` calling `history.back()`). Easy to miss because the page still renders correctly otherwise; the only symptom is the user being stranded.
- **BouncyCastle's `GcmBlockCipher(new AesEngine())` works correctly under Blazor WebAssembly** — verified both live (browser E2EE message round-trip) and via xUnit (encrypt-then-decrypt, wrong-secret throws `InvalidCipherTextException`). Confirms the project's "fully managed crypto so MAUI and WASM run identical code" approach (already used for ML-DSA/ML-KEM) extends cleanly to symmetric AES-GCM — no need to reach for `System.Security.Cryptography.AesGcm`, which is native-backed and was the whole reason the PQC primitives went with BouncyCastle in the first place.
