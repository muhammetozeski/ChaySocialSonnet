# Session token expiry + real server-side revocation on sign-out

Kategori: protection | Efor: M | Rank: 30

## Ne
In ChaySocialSonnet.Web/Backend/LocalIdentityRegistry.cs the `sessions` dictionary is `ConcurrentDictionary<string, string>` (token -> publicId) with no expiry at all - contrast with `PendingChallenge` two lines above it, which already has an `ExpiresAt` and a `ChallengeLifetime` constant. Change `sessions` to store a small record `SessionRecord(string PublicId, DateTimeOffset ExpiresAt)`, add a `static readonly TimeSpan SessionLifetime = TimeSpan.FromHours(...)`, set `ExpiresAt` in `VerifyChallengeAsync`, and in `ResolveSessionAsync` check `ExpiresAt >= DateTimeOffset.UtcNow` (removing and returning null if expired, same pattern already used for challenges). Then add `Task RevokeSessionAsync(string sessionToken)` to `IIdentityRegistry` (MainProject/Backend/IIdentityRegistry.cs) and implement it as `sessions.TryRemove(sessionToken, out _)`. Add `POST /api/identity/signout` in ChaySocialSonnet.Web/Backend/IdentityEndpoints.cs that reads the bearer token via the existing `RequestAuthentication.ResolveActingPublicIdAsync` pattern and calls `RevokeSessionAsync`. Add `IdentityApiClient.SignOutAsync()` (MainProject/Services/Identity/IdentityApiClient.cs) and call it from Profile.razor's `HandleSignOut` (line 136-139) before `AuthService.SignOut()` clears local state.

## Neden
Right now a session token, once issued, is valid forever - and clicking 'Sign Out' in Profile.razor only calls `AuthService.SignOut()`, which is purely client-side (clears `CurrentIdentity`/`SessionToken` in memory and raises an event) and never tells the server to invalidate anything. A token that leaked once (browser dev tools, a shared/borrowed machine, a captured request) stays usable to act as that identity indefinitely, even after the legitimate user explicitly 'signs out'. This closes that gap with the smallest possible change, reusing the expiry pattern the codebase already has for challenges.
