# Fix LocalLikeStore's non-atomic toggle race and add store concurrency tests

Kategori: resilience | Efor: S | Rank: 20

## Ne
LocalLikeStore.ToggleLikeAsync computes `bool nowLiked = !likers.TryRemove(likerPublicId, out _) && likers.TryAdd(likerPublicId, 0);` - TryRemove and TryAdd are each atomic individually but the pair is not: under two concurrent calls for the same post+liker (a real scenario since PostCard.razor's like button, HandleToggleLike at MainProject/UI/Elements/Cards/PostCard.razor:84-91, is only disabled when ViewerPublicId is null, not while a request is in flight, so a fast double-click/double-tap fires two overlapping POST /api/posts/{postId}/like calls), the reported nowLiked can disagree with the actual dictionary state (e.g. both calls see TryRemove fail, one wins TryAdd and correctly reports true, the other loses TryAdd and reports false/'unliked' even though the like is now persisted). Fix by taking a `lock (likers)` around the check-then-act in LocalLikeStore.cs so the toggle is atomic per post. Add MainProject.Tests/Backend/LocalLikeStoreTests.cs with a concurrency test that fires N parallel ToggleLikeAsync calls from the same liker via Task.WhenAll and asserts the final HasLikedAsync state matches the parity of N and that no response's nowLiked ever disagreed with the state immediately after it completed. While in that test file, also add basic coverage for LocalFollowStore, LocalCommentStore, LocalBlockStore, LocalNotificationStore and LocalReportStore, none of which have any tests today despite MainProject.Tests already covering LocalPostStore, LocalMessageRelay and LocalIdentityRegistry.

## Neden
The like button is the single most-clicked control in the app and the toggle response is what PostCard.razor trusts to update its optimistic UI state - a rapid double-tap (very common on touch) can desync what the client shows from what the server actually persisted, and six of the nine Local* stores currently have zero test coverage.
