# Wrap the router in a Blazor ErrorBoundary

Kategori: resilience | Efor: S | Rank: 13

## Ne
MainProject/UI/Routes.razor renders `<RouteView RouteData="@routeData" DefaultLayout="@typeof(...MainLayout)" />` directly inside `<Found>` with no ErrorBoundary anywhere in the tree (confirmed: grepping the whole repo for "ErrorBoundary" returns zero matches). Wrap that RouteView in Blazor's built-in `<ErrorBoundary>` component, with `<ChildContent>` holding the existing RouteView/FocusOnNavigate and `<ErrorContent>` showing a plain "Something went wrong" message plus a reload action, styled via a small new Routes-level or MainLayout-level CSS partial instead of the framework's default raw red exception text.

## Neden
The whole app is one InteractiveWebAssembly render tree (HostRenderMode.Interactive per App.razor/Routes.razor) and currently has zero fault containment: confirmed by reading MainProject/UI/Routes.razor (no ErrorBoundary) and grepping the tree for the component (no matches anywhere). An unhandled exception thrown during rendering or in any lifecycle method on any page - including Home.razor's OnInitializedAsync, which today calls `await PostApi.GetRecentPostsAsync(...)` with no try/catch and would surface exactly this - currently has no app-level fallback, so the user is left looking at a dead page or raw exception output with only a full reload to recover. This is a single, small, page-count-independent safety net rather than a per-page fix, which matters more while the app is still adding pages.
