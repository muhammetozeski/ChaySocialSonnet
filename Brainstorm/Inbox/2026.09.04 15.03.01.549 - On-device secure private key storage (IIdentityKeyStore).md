# On-device secure private key storage (IIdentityKeyStore)

Kategori: protection | Efor: M | Rank: 9

## Ne
Add an `IIdentityKeyStore` abstraction alongside `MainProject/Services/Identity/IdentityService.cs` and `ChayIdentity.cs` (e.g. `MainProject/Services/Identity/IIdentityKeyStore.cs` with `SaveAsync(ChayIdentity)` / `LoadAsync()` / `ClearAsync()`), with two concrete implementations registered per host: a MAUI implementation backed by `Microsoft.Maui.Storage.SecureStorage` for Windows/Android, and a WASM implementation for the Blazor host. Confirmed by reading the files: `IdentityService.GenerateIdentity()` only returns a `ChayIdentity` record holding raw `SigningPrivateKey`/`EncryptionPrivateKey` byte[] in memory, and there is no persistence code anywhere in the repo — `AuthService.cs` is a 15-line stub with just an event and `IsLoggedIn` flag, no storage calls.

## Neden
The queued Login/Splash pages will need to persist the generated `ChayIdentity` somewhere, and without a dedicated storage abstraction in place first, that persistence will get invented ad hoc under the time pressure of building the UI page — e.g. plain `SecureStorage.SetAsync` of raw bytes on MAUI, or an unencrypted localStorage/IndexedDB entry on WASM. The ML-DSA/ML-KEM private keys are the entire security premise of the app; getting their storage wrong once means they end up in an easily-dumped plaintext location. This is a small, self-contained interface plus two host implementations, not a redesign, so it fits a project still laying its foundation.
