# Passphrase-encrypted identity backup file (export/import)

Kategori: resilience | Efor: M | Rank: 20

## Ne
Add IdentityBackupService (new file MainProject/Services/Identity/IdentityBackupService.cs) with two static methods: EncryptBackup(ChayIdentity identity, string passphrase) -> byte[] and DecryptBackup(byte[] blob, string passphrase) -> ChayIdentity. Derive a 32-byte AES key from the passphrase with a random 16-byte salt via System.Security.Cryptography.Rfc2898DeriveBytes.Pbkdf2 (SHA-256, ~200k iterations - this is a managed .NET API, already proven WASM-safe by IdentityService's own SHA256.HashData usage), then encrypt JsonSerializer.Serialize(identity) with the same GcmBlockCipher/AesEngine pattern IdentityService.EncryptMessage already uses. Output layout: salt(16) + nonce(12) + ciphertext+tag. Wire it into two existing pages: Profile.razor gets a 'Back up identity' button next to the existing DangerButton sign-out that prompts for a passphrase then downloads the blob via IJSRuntime (Profile.razor already injects IJSRuntime for the clipboard copy) using a small Blob+anchor-click JS call, filename chay-backup-{PublicId}.bin. Login.razor gets a 'Restore from backup' secondary button using an <InputFile> to read the uploaded bytes plus a passphrase prompt, then runs the same flow HandleContinue already does: ApiClient.SignInAsync(identity) to verify with the server, KeyStore.SaveAsync(identity), AuthService.SignIn(identity), navigate to /home.

## Neden
Right now IIdentityKeyStore only ever holds the private key in this device's SecureStorage/localStorage (WasmIdentityKeyStore, MauiIdentityKeyStore) - clearing browser data or losing the device loses the account permanently, with zero recovery path. A self-custodied encrypted backup file is the minimal fix: the user keeps one file somewhere safe (their own Drive/USB) and can restore on any device without ever putting the raw private key on disk or trusting the server with anything but a JSON blob it never receives at all.
