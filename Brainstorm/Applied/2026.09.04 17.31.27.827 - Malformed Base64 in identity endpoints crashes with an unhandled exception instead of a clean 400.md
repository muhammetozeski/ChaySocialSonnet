# Malformed Base64 in identity endpoints crashes with an unhandled exception instead of a clean 400

Kategori: protection | Efor: S | Rank: 13

## Ne
ChaySocialSonnet.Web/Backend/IdentityEndpoints.cs calls Convert.FromBase64String on three fields straight from the request body with no guard: request.SigningPublicKeyBase64 and request.EncryptionPublicKeyBase64 in the /api/identity/register handler (lines 13-14), and request.SignatureBase64 in the /api/identity/verify handler (line 39). Any malformed value throws an uncaught FormatException. Program.cs only registers app.UseExceptionHandler("/Error") inside the non-Development else branch (lines 47-51), so in Development this is a raw unhandled crash and in production it's a generic /Error redirect that doesn't say which field was bad. Replace each Convert.FromBase64String call with Convert.TryFromBase64String (or a try/catch) and return Results.BadRequest naming the offending field.

## Neden
These are the three pre-authentication identity endpoints — register and verify are literally how a client proves who it is, so there's no signed-in session to have gone wrong first. Any client sending a slightly malformed key or signature (truncated copy-paste, a future client bug, a proxy that mangles the body) currently reaches raw crypto-decoding code with zero validation and takes the whole request down instead of getting a clear 400. It's a concrete bug hit today, not a speculative future concern, and the fix is small and contained to one file.
