# AppEvent.Raise() tek bozuk handler'da zinciri kesiyor

Kategori: resilience | Efor: S | Rank: 9

## Ne
In `MainProject/Events/AppEvent.cs`, both `AppEvent.Raise()` (lines 19-25) and `AppEvent<T>.Raise(T)` (lines 43-49) call handlers sequentially via `foreach (var handler in handlers.ToArray()) handler();` with no try/catch. If a handler throws, the foreach stops there, every handler subscribed after it never gets called, and the exception propagates directly to the code that called Raise() (e.g. `ThemeManager.Apply`, `MainProject/UI/ThemeConstants/ThemeManager.cs` lines 15-20). Wrap each handler call in its own try/catch, collect thrown exceptions, and after the loop finishes throw a single `AggregateException` if any were collected. Add a test to `MainProject.Tests` verifying that "if one handler throws, the others are still called".

## Neden
Right now, if one subscriber (e.g. a page/component) throws during render, every other part subscribed to the same event (e.g. another component that should also reflect the theme) silently stays unupdated, and the calling code on top also gets an unexpected exception. With the event system already moved to a HashSet-based design and code like ThemeManager already actively using it on every Raise(), a single broken subscriber being able to lock up the whole chain is the most fragile point in the architecture right now. Low effort and narrow scope, and it improves code that is already working and tested, which makes it higher priority than the other two candidates (static fields nothing reads yet, crypto methods that don't yet receive real external bytes).
