# Actually enforce blocks in the feed and comments (currently a no-op)

Kategori: protection | Efor: S | Rank: 20

## Ne
Verified in ChaySocialSonnet.Web/Backend/PostEndpoints.cs that /api/posts/recent, /api/posts/by-author/{authorPublicId}, and GET /api/posts/{postId}/comments never consult IBlockStore at all — MainProject/Backend/IPostStore.cs's GetRecentPostsAsync/GetPostsByAuthorAsync take no viewer parameter, and PostEndpoints only uses the viewerPublicId query param to resolve like-status via ILikeStore. So a user you block still shows up in your feed, still shows up on their own profile when you visit it, and their comments still render on posts. Fix: inject IBlockStore into those three handlers; when resolving each PostSummary, skip posts/comments where the viewer has blocked the author OR the author has blocked the viewer (use the existing IBlockStore.IsBlockedAsync both directions). Concretely, add a static filter helper in PostEndpoints.cs that runs before ToSummariesAsync, e.g. `posts = posts.Where(p => !await blocks.IsBlockedAsync(viewerPublicId, p.AuthorPublicId) && !await blocks.IsBlockedAsync(p.AuthorPublicId, viewerPublicId))` (guarded for viewerPublicId is null). No new store or interface needed — LocalBlockStore.cs already has the bidirectional lookup, it's just never called from the read path.

## Neden
This is the single biggest safety gap in the app today: the Block button on UserProfile.razor makes the user believe blocking works, but the blocked person's posts and comments keep appearing everywhere. Silently non-functional protection is worse than no protection button at all because it gives false confidence.
